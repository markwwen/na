# 从 agent-proposal 到 na 的最小项目框架

这份评审针对 na 的 `/init` 实现。提案中的渐进加载、验证反馈和知识归属值得保留；推荐目录树适合作为扩展选项，不适合作为所有项目的默认模板。

## 更强模型改变了什么

OpenAI 在 [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) 中建议重新审视累积的提示词：缩短 skill 描述并明确适用场景，按需读取文档，避免过度细化步骤和为小改动强制执行广泛检查。

这支持精简指导层。它不能直接证明整套 harness 已不重要：工具执行、进程取消、状态保存、上下文组织和外部验证，仍由运行时及项目环境提供。更少的人工步骤是设计方向，具体减少到什么程度应以本项目的任务结果验证。

na 当前使用的模型由用户配置决定；生成的项目框架不假定所有使用者都采用 GPT-6，也不包含仅适用于某个模型的推理提示词。

## 基本原则

| 提案 | 保留的价值 | 优化方式 |
|---|---|---|
| 薄而稳定的入口 | 让 agent 找到项目事实和关键约定 | 只写难以从代码发现的事实和指向相关资料的入口；不要求每次修改前阅读整套文档 |
| 渐进加载 | 减少不相关内容占据上下文 | 每个 skill 描述清楚触发条件；少量高价值专项 skill 优于大量通用规则 |
| 确定性命令 | 降低反复猜测运行方式的成本 | 优先复用 package scripts、Makefile 和 CI；只有重复操作确实需要组合时才新增脚本 |
| 验证优先 | 使用可观察结果检查改动 | 区分“发现命令”“执行成功”“覆盖验收条件”；通过若干测试不能自动推出所有行为正确 |
| 指令与强制策略分离 | 避免把自然语言当权限控制 | 具体说明强制点；hook 的效果取决于触发事件和失败处理，不能笼统视为完整沙箱 |
| 知识分层 | 区分稳定事实、流程和临时状态 | 保留职责分层，复用现有 docs；不为凑齐层次强制生成 `.ai/`、worklog 等空文件 |
| 跨工具复用 | 项目知识归仓库所有 | 采用 AGENTS.md 和标准 skill 文件；特定工具的适配与权限配置按需添加，不机械复制多套配置 |

提案中各工具的发现路径、优先级和引用方式属于具体产品行为，不应写成统一标准。na 的行为以 README 和实现为准。例如 na 当前仅加载 Git 根目录到启动目录的指令链，不预加载仓库所有嵌套指令。

## `/init` 的默认产物

```text
AGENTS.md
.agents/skills/verify-project/SKILL.md
.agents/skills/verify-project/references/commands.md
```

三个文件分别承担导航、选择验证方式、保存项目命令事实的作用。命令清单只保存入口和来源，不复制脚本正文，不自动执行命令。初始化不调用 LLM；项目用途、业务不变量和架构边界保留为待补充事实。

这是一版可运行的基础框架。复杂任务仍可由普通对话分析源码、补充项目约定、更新命令清单。先从实际使用中发现重复困难，再提炼成新的专项 skill。

## 应保持的运行时能力

- 项目指令加载和来源可见，变更后可重载。
- 工具调用、超时、取消和错误回传。
- 完整会话归档、恢复和上下文压缩。
- 初始化只创建缺失项，避免覆盖团队已有约定。
- 真正需要强制控制的操作，在权限、工具、CI 或隔离环境中实现。

本次新增项目指令加载与 `/reload`，让 `/init` 生成的文件立即对当前会话生效。文件指导和 skills 都没有被当作强制权限系统。

## 以后用什么衡量效果

挑选同一组真实小任务，对比无项目框架与最小框架：一次缺陷修复、一次涉及多个文件的功能改动、一次小文档修改。固定模型与运行环境，记录完成率、实际验证结果、工具调用次数、耗时，以及需要人工补充的信息。

只有某项说明稳定改善结果时才加入默认入口；如果它让简单任务多读文件、多跑无关检查，就缩小适用范围或移入专项 skill。生成文件数量和提示词长度都不应成为进度指标。
